Content work becomes stressful when the writing tool and the website disagree.
A field is missing, an image uses the wrong format, or a last-minute change
cannot be traced after deployment. Outstatic reduces that friction by keeping
the editorial model close to the code that consumes it.

The result is not a complicated new workflow. It is a clearer version of tools
the team already understands.

## Collections give every document a home

An Outstatic project organizes related documents into collections. A blog can
have Posts, a marketing site can add Pages, and a portfolio can keep Projects
separate from both.

Each collection has its own schema and content directory:

```text
outstatic/
  content/
    posts/
    pages/
    projects/
```

This structure is useful in the dashboard and in the repository. Editors can
find the right content quickly, while developers can reason about file paths,
queries, and routes without reverse-engineering a remote content model.

## Custom fields turn conventions into controls

Editorial guidelines often begin as a document: include a description, choose
a cover image, add the right category, and keep the SEO title concise. In
Outstatic, those rules can become fields in the collection schema.

Writers see labels and controls instead of raw YAML. The saved file still
contains straightforward frontmatter:

```yaml
title: 'A new product story'
status: 'draft'
category: 'news'
featured: false
```

The frontend receives predictable values, and editors spend less time checking
whether they followed an invisible format.

## Draft, review, and publish with useful history

Status and publication dates make it easy to separate drafts from live posts.
When a change is saved, the repository records what changed and when. Teams can
use that history to inspect an edit, restore an earlier version, or understand
why a deployment changed.

Because the files live with the application, existing GitHub and deployment
practices can remain in place. A content commit can trigger a site build just
like a code commit, while branches can support previews or review when the
project needs them.

## Reuse patterns without making writers code

Markdown covers most articles. When a site needs richer content, MDX and
Outstatic's Block Library let developers register reusable components such as
callouts, videos, product cards, or embeds.

Editors insert a block from the slash menu and complete a small form for its
properties. The document saves the MDX component, and the frontend renders it
with the project's own React implementation.

That division of responsibility keeps everyone in a comfortable place:
developers build durable presentation components, and writers compose them
without copying JSX by hand.

## Keep the workflow understandable

Outstatic works best when the content model stays intentional. Begin with the
collections and fields the site already needs. Add blocks when a pattern is
genuinely reusable. Let Git provide history, and let Next.js own rendering.

The calm comes from knowing where everything lives: the dashboard is the
editor, Markdown is the content, GitHub is the history, and your application is
still the website.
